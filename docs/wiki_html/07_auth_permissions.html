7. Authentication & Permissions

Authentication System

The system uses username + password authentication via Django's built-in auth and django-allauth.

  • Email login is disabled (ACCOUNT_LOGIN_METHODS = {'username'})
  • Social authentication is configured but not actively used
  • Email verification is off (ACCOUNT_EMAIL_VERIFICATION = 'none')
  • Auto-logout after 30 minutes of inactivity (production)

Login Flow

Browser POST /accounts/login/
    │
    ▼
django-allauth AccountAdapter.login()
    │ validates username + password
    ▼
Django session created (stored in Redis)
    │
    ▼
Redirect to /login-success/
    │ (determines role-based redirect target)
    ▼
User lands on their default dashboard

Password Requirements

Enforced by custom validators in config/settings/base.py:
- Minimum 8 characters
- At least 3 digits
- At least one uppercase letter
- At least one lowercase letter
- At least one special symbol

Passwords are hashed with Argon2 (preferred), falling back to PBKDF2 and BCrypt.

Session Security

  • Session cookie: HttpOnly, Secure, SameSite=Lax
  • CSRF protection: enabled on all state-changing requests
  • Idle timeout: 30 minutes (production), 1000 minutes (development)
  • Implemented via AutoLogout middleware in middleware.py

Rate Limits (Production)

ACCOUNT_RATE_LIMITS = {
    "login_user":     "10/m",    # 10 attempts per minute
    "login_failed":   "5/5m",    # 5 failures per 5 minutes
    "signup":         "3/h",     # 3 new accounts per hour
    "email":          "10/m",
    "password_change": "5/h",
}

Authorization System

Authorization uses Django's Group-based permissions. Each user belongs to one or more groups, and views check group membership to allow or deny access.

User Roles (Groups)

Group Name Access Level Description
MSCC MSCC module Basic MSCC data entry — register children, record services, mark attendance
MSCC_CENTER MSCC center-scoped Same as MSCC but limited to their assigned center
MSCC_FULL MSCC unrestricted No center/partner filter — can see all MSCC data
MSCC_PARTNER MSCC partner-scoped See all data for their assigned partner organization
MSCC_UNICEF MSCC read-only analytics Can view dashboards and run reports across all partners
CLM_ATTENDANCE CLM attendance only Can only record CLM attendance
CLM_Bridging CLM bridging data entry Register students, record CLM services
CLM_BRIDGING_ALL CLM bridging admin Full CLM bridging access across partners
CLM_TEACHER CLM teacher management Add/edit CLM teachers
EXPORT Data export Access to export functionality
Superuser Everything Full Django admin access

Data Scoping Rules

Most views filter querysets based on the logged-in user's assignments:

# Example — how MSCC list view filters data
def get_queryset(self):
    user = self.request.user
    qs = Registration.objects.filter(deleted=False)

    if user.groups.filter(name='MSCC_FULL').exists():
        return qs  # No filter — sees everything

    if user.groups.filter(name='MSCC_PARTNER').exists():
        return qs.filter(partner=user.partner)

    if user.groups.filter(name='MSCC_CENTER').exists():
        return qs.filter(center=user.center)

    # Default MSCC: filter by center
    return qs.filter(center=user.center)

The User model stores assignment context:
- user.partner — Restricts to a single partner organization
- user.center — Restricts to a single center
- user.centers (M2M) — Multi-center access
- user.school / user.schools — School assignments

Checking Groups in Views

Using GroupRequiredMixin (CBV):

from braces.views import GroupRequiredMixin

class MyView(GroupRequiredMixin, ListView):
    group_required = ['MSCC', 'MSCC_FULL']  # Any of these groups

Manual check in a view:

def my_view(request):
    if not request.user.groups.filter(name__in=['MSCC', 'MSCC_FULL']).exists():
        raise PermissionDenied

In templates:

{% load has_group %}

{% if request.user|has_group:"MSCC_FULL" %}
    <a href="{% url 'mscc:export' %}">Export All Data</a>
{% endif %}

The has_group template tag is defined in student_registration/contrib/.

REST API Authentication

DRF uses:
- Session authentication — Automatic for browser clients (uses Django session cookie)
- Token authentication — For programmatic API access

Configuration in base.py:

REST_FRAMEWORK = {
    'DEFAULT_AUTHENTICATION_CLASSES': (
        'rest_framework.authentication.SessionAuthentication',
        'rest_framework.authentication.TokenAuthentication',
    ),
    'DEFAULT_PERMISSION_CLASSES': (
        'rest_framework.permissions.IsAuthenticated',
    ),
}

All API endpoints require a logged-in user — there are no public endpoints.

Managing Users & Roles

Via Admin Panel

  1. Go to /admin/users/user/
  2. Create or edit a user
  3. Set their partner, center, school assignments
  4. Under Permissions → Groups, assign the appropriate role group

Creating Groups

Groups must be created before users can be assigned to them. Either:
- Create via /admin/auth/group/
- Or via a data migration / management command

Programmatic User Creation

from django.contrib.auth import get_user_model
from django.contrib.auth.models import Group

User = get_user_model()
user = User.objects.create_user(
    username='fieldworker1',
    password='Secure@Pass123',
    partner_id=5,
    center_id=12,
)
group = Group.objects.get(name='MSCC_CENTER')
user.groups.add(group)

Activity Logging

Every HTTP request is recorded in the UserActivity model by the UserActivityMiddleware:

  • Logs: username, URL path, HTTP method, POST data (sanitized), IP address, user agent
  • Admin requests (/admin/) are excluded
  • Stored in backends_useractivity table
  • Viewable via the admin panel at /admin/backends/useractivity/

This provides a full audit trail for compliance and debugging.
