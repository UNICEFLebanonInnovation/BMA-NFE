4. Database Schema & Models

All models use Django's ORM. The database is PostgreSQL. This page documents every significant model, its key fields, and how models relate to each other.

users App

User

Extends Django's AbstractUser. Every person who logs in has a User record.

Field Type Notes
username CharField Login credential (email login disabled)
email EmailField Stored but not used for login
partner FK → PartnerOrganization The NGO/partner this user belongs to
school FK → School Primary school assignment (nullable)
location FK → Location Primary location (nullable)
center FK → Center Primary center assignment (nullable)
locations M2M → Location Multi-location access list
schools M2M → School Multi-school access list
regions M2M → Location Regional access (related_name regions)
phone_number CharField Optional contact number

The partner, school, center, and location fields control what data the user can see — most views filter querysets based on request.user.partner or request.user.center.

Login

Field Type Notes

created DateTimeField When the session was created

Field Type Notes

Field Type Notes

Location

Hierarchical tree of geographic areas using MPTT (Modified Preorder Tree Traversal). Lebanon's geography: Governorate → Caza → Cadaster → Locality.

Field Type Notes
name CharField Arabic or English place name
name_ar CharField Arabic name
parent TreeForeignKey → Location Parent node in the tree
type FK → LocationType Level in the hierarchy

MPTT adds lft, rght, tree_id, level columns automatically for fast subtree queries.

Key Database Conventions

  • All models use Django's default AutoField (integer primary keys), not BigAutoField
  • Soft deletes are used in Registration (deleted = BooleanField(default=False)) rather than hard deletes
  • TimeStampedModel from django-model-utils is used as a base for models that need created/modified timestamps
  • MPTT is only used for the Location model
  • No raw SQL — all queries go through the ORM
