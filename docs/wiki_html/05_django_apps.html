5. Django Apps Reference

The project is organized as a standard Django project with multiple apps, each owning a specific domain. All apps live under student_registration/.

App Directory

student_registration/
├── accounts/          Thin wrapper — account-related views/templates
├── attendances/       MSCCAttendance and CLMAttendance tracking
├── backends/          Async export jobs, user activity logging
├── child/             Child demographic profile model
├── clm/               Community Learning Management program
├── contrib/           Shared utilities, custom Sites migration
├── dashboard/         Analytics and reporting views
├── locations/         Location hierarchy (MPTT), Centers
├── mscc/              MSCC service delivery (the primary module)
├── schools/           Schools, sections, partner organizations
├── students/          Student model, nationalities, ID types
├── taskapp/           Celery app initialization
└── users/             Custom user model, auth adapters, groups

users

Owns: Authentication, user profiles, group/role management, Firebase token storage.

Key files:
- models.py — User, Login, WebPushToken
- admin.py — User admin with import/export
- adapters.py — django-allauth account adapter
- views.py — Profile page, language switcher

The User model is the central spine of authorization. Most views check request.user.partner, request.user.center, or group membership to filter querysets.

mscc

Owns: Everything related to the MSCC (Multi-Service Community Centers) program — registrations, service delivery, teachers, rounds, attendance, exports, dashboards.

This is the largest and most complex app in the system (~2,686 lines of models alone).

Key files:
- models.py — Registration, Child, Round, Teacher, all service models
- views.py — List, add, edit, profile views; AJAX service delivery endpoints; dashboard views
- urls.py — All /mscc/ routes
- admin.py — Admin registrations with import/export and custom filters
- tasks.py — Celery generate_mscc_export task
- serializers.py — DRF serializers for API endpoints
- forms.py — Registration and service delivery forms
- resources.py — django-import-export resource definitions

clm

Owns: Community Learning Management — bridging program enrollment, CLM attendance, CLM teacher management, assessments.

Structure mirrors mscc but for the CLM program type. CLM-specific models include CLM, Bridging, BridgingService, and cycle-based attendance.

attendances

Owns: Attendance models and attendance recording views for both MSCC and CLM.

Key files:
- models.py — MSCCAttendance, MSCCAttendanceChild, CLMAttendance, CLMAttendanceStudent
- views.py — Attendance entry, attendance child view, attendance report, heatmap

The attendance heatmap endpoint is also exposed via the DRF API (AttendanceHeatmapViewSet).

child

Owns: The Child model — the shared demographic record used by both MSCC registrations.

The Child model is intentionally kept separate from program-specific data so that a child can be registered across multiple programs without duplicating demographics.

students

Owns: The Student model (used by CLM), and reference data: Nationality, IDType, Labour.

The distinction between Child (MSCC) and Student (CLM) is historical — both represent a person, but they have slightly different fields and were developed for different programs.

schools

Owns: School, Section, PartnerOrganization, Club, Meeting, CommunityInitiative, HealthVisit, PublicHolidays.

Partner organizations are central to access control — almost every record is scoped to a partner. Schools are used for formal enrollment tracking within MSCC registrations.

locations

Owns: LocationType, Location (MPTT tree), Center.

The Location model uses MPTT for efficient subtree queries. Lebanon's hierarchy is:

Governorate (e.g., Beirut)
  └── Caza (e.g., Beirut)
       └── Cadaster (e.g., Ashrafieh)
            └── Locality / Village

Center maps to a specific cadaster-level location and partner organization.

backends

Owns: ExportHistory (tracks async export jobs), UserActivity (HTTP audit log), export generation logic, Azure Blob storage backend, activity logging middleware.

Key files:
- models.py — ExportHistory, UserActivity
- export.py — Core export generation functions called by Celery tasks
- storage.py — Custom storage backend configuration

dashboard

Owns: Analytics and summary views. Queries aggregate data across registrations, services, and attendance for charts and KPI tiles.

Views in this app tend to be read-only and query-intensive — they rely heavily on Django ORM aggregations (annotate, values, Count, Sum).

accounts

A thin app providing account-related template views (login, password reset) that wrap django-allauth.

taskapp

Celery application initialization. Contains only the Celery app definition and autodiscover_tasks() call. All actual tasks are defined in their respective app tasks.py files.

contrib

Shared utilities and customizations:
- Custom migration for Django's sites framework
- Shared template tags and filters (e.g., has_group template tag)

Adding a New App

# 1. Create the app
python manage.py startapp my_new_app student_registration/my_new_app/

# 2. Register it in config/settings/base.py
LOCAL_APPS = [
    ...
    'student_registration.my_new_app',
]

# 3. Create and apply migrations
python manage.py makemigrations my_new_app
python manage.py migrate

# 4. Add URL patterns in config/urls.py
urlpatterns += [path('my-app/', include('student_registration.my_new_app.urls'))]
