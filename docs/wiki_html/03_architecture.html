Backend Framework: Django 5.2.7

Django is used in its classic "batteries-included" style:

  • ORM for all database access (no raw SQL in normal flows)
  • Class-based views (CBVs) throughout, mixed with some function-based views
  • Django templates for all HTML rendering (server-side)
  • Django admin (Jazzmin-enhanced) as the primary back-office tool
  • Django REST Framework (DRF) for the JSON API layer
  • django-allauth for authentication flows

Settings Architecture

Settings are split into four files under config/settings/:

base.py          ← shared configuration (always loaded)
local.py         ← extends base for local development
production.py    ← extends base for production (SSL, Sentry, etc.)
test.py          ← extends base for pytest runs

DJANGO_SETTINGS_MODULE environment variable selects the active settings file.

Database: PostgreSQL

  • Driver: psycopg v3 (modern psycopg3, not psycopg2)
  • Default database name: mscc_10012023
  • Atomic requests enabled: each HTTP request is wrapped in a transaction
  • MPTT extension used for the Location model (geographic hierarchy tree)

All Django apps use the ORM exclusively. Migration files live in each app's migrations/ directory and must be committed to version control.

Async Tasks: Celery 5.5 + Redis

Celery handles operations that are too slow for an HTTP request:

  • Export generation — Building XLSX/CSV files for hundreds of rows
  • Email sending (in production)
  • Scheduled jobs via django-celery-beat

Two task queues are configured:
- default — General tasks
- mscc_export — Heavy export jobs (max concurrency = 1 to prevent DB overload)

In local development, CELERY_TASK_ALWAYS_EAGER = True causes tasks to run synchronously inline — no worker process needed.

File Storage: Azure Blob Storage

In production, all uploaded media and generated export files are stored in Azure Blob Storage via django-storages. The Django DEFAULT_FILE_STORAGE and MEDIA_URL settings point to the Azure backend.

In development, the standard FileSystemStorage is used (files land in student_registration/media/).

Notifications: Firebase Cloud Messaging

When a background export completes, the system sends a push notification to the requesting user's browser via Firebase Cloud Messaging (FCM). FCM tokens are stored in the WebPushToken model (one per user device/browser session).

Search & Autocomplete

  • django-autocomplete-light + Select2 — Used on foreign key fields throughout the admin and public-facing forms for school, location, partner lookups
  • fuzzywuzzy / Levenshtein — Used in the duplicate-check logic when registering a child (fuzzy name matching to catch near-duplicates)

Admin UI: Jazzmin

The Django admin is enhanced with Jazzmin, which provides:
- A Bootstrap 4-based sidebar layout
- Font Awesome icons per model
- Configurable top-menu links
- Custom welcome message and branding

All configuration is in JAZZMIN_SETTINGS inside config/settings/base.py.

Full System Flow

The following describes the end-to-end data flows for the two most critical operational modules.

Registration Flow

  1. User opens the registration form.
  2. Inputs child data (name, DOB, nationality, household info, etc.).
  3. Form validates data on both frontend (JS) and backend (Django Forms).
  4. Data saved into the Registration model linked to a Round.
# Backend date validation example
def clean(self):
    date = self.cleaned_data.get("registration_date")
    if date < self.instance.round.start_date:
        raise ValidationError("Invalid date")

Attendance Flow

  1. User selects center, round, and programme.
  2. System fetches registrations filtered by those parameters.
  3. Filters further based on programme section.
  4. Displays the filtered list for attendance marking.
  5. User marks each student as Present / Absent / Excused / Late.
  6. Records saved to the attendance table upon submission.
# Core attendance query
registrations = Registration.objects.filter(
    center_id=center_id,
    round_id=round_id
)

Layered Application Architecture

The system is organized into distinct technical layers to separate concerns and reduce coupling:

LayerResponsibility
AuthenticationLogin, session management, role enforcement
Identity ManagementChild profiles, family data, duplicate detection
Programme OperationsRegistration, enrolment, service delivery
Attendance ManagementDaily attendance, absence tracking, headcount
ReportingPivot dashboards, exports, statistics
Infrastructure IntegrationsAzure Blob, Firebase FCM, Unique ID API

Database Domain Groups

The database is logically grouped into business domains:

  • Child / Student Identity Hub — Core child record, identification, nationalities
  • Registration Nexus — Links child to programme, round, center, and section
  • Location / Facility Hierarchy — Country → Governorate → District → Center
  • Attendance — Daily records per registration per date
  • Education Services — Programme assignments, grades, assessments
  • Reporting — Database views (vw_mscc_attendance_absence, etc.) used by exports

Application Version

The current system version is tracked in config/settings/base.py:

COMPILER_VERSION = '2.35'

This version string is available in templates via the settings context processor.
